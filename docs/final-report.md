# 미로 베팅 게임 최종 보고서

2026-10-02 기준. 요청하신 것은 세 가지였습니다. (1) n×n 미로에서 출구를 찾는 commit-reveal 베팅 게임을 만들 것, (2) 플레이어가 이 게임으로 날먹할 수 있는지 확인할 것, (3) 시뮬레이션을 1,000회 이상 돌려 흥미를 잃지 않으면서 하우스가 더 잘 먹는 구조로 맞출 것. 이 문서는 그 세 가지의 답을 먼저 적고, 근거와 한계를 뒤에 적습니다.

## 1. 결론

### 게임은 동작하는가

동작합니다. 로컬 체인(Anvil)에서 `pnpm dev:up` 한 번으로 뜨고, 브라우저에서 지갑을 연결해 크기를 고르고 베팅하면 안개 낀 미로가 나옵니다. 한 칸씩 움직이고, 되돌아갈 수 없고, 걸을수록 환불 가능액이 줄고, 중간에 그만두면 그 금액을 받고, 막다른 칸에 들어가면 전부 잃고, 출구에 닿으면 베팅액 × 배율을 받습니다. 판이 끝나면 서버 시드가 공개되어 미로를 다시 만들어 대조하는 검증 화면이 열립니다.

- 자동 검사: 단위·통합·컨트랙트 테스트와 브라우저 시나리오 10개로 확인합니다(§7). 개수와 결과는 독립 검토(§12)의 수정이 끝난 뒤 다시 돌려 적습니다. 수정 진행 중 — 최종 확인 후 갱신.
- 브라우저 시나리오는 지금 적용된 표로도 돌렸고, 세 크기(5×5, 7×7, 9×9)를 각각 한 판 이상 플레이했습니다(§8).
- 한계: 브라우저 시나리오는 정답 경로를 미리 계산해야 해서 테스트용 시드 생성 장치를 켜고 돕니다. 실제 무작위 시드로 브라우저에서 끝까지 도는 자동 실행은 없습니다. 이번 단계에서 수동으로 한 번, 화면 없이 서버와 체인만 상대로 무작위 시드 네 판을 돌려 정산과 검증이 맞는 것을 확인했습니다(§7). 독립 검증에서도 검증자가 직접 14판을 플레이했고, 그중 8판은 테스트 장치 없이 실제 무작위 시드였으며 2판이 출구에 도착했습니다(§12). 둘 다 사람이 한 번 해 본 것이고 저장소의 자동 검사에는 들어 있지 않습니다.
- 로컬 체인에서만 돌려 봤습니다. 테스트넷이나 메인넷 배포는 범위 밖이었습니다.

### 플레이어가 날먹할 수 있는가

세 수준으로 나눠 답합니다. 확실한 정도가 서로 다르기 때문입니다.

1. **컨트랙트가 강제하는 것 (증명됨).** 아래는 컨트랙트 코드가 막습니다. 지급액은 온체인 표와 일치해야 하고, 한 판의 지급은 예약된 최대 금액을 넘지 못하며, 정산은 서버 시드가 공개되어야만 되고, 같은 서명을 두 번 쓸 수 없고, 정산 기한 전에는 회수가 안 되고 기한 뒤에는 정산이 안 됩니다. 받는 쪽이 수령을 일부러 실패시켜도 정산은 되돌려지지 않습니다. 캐시아웃은 어느 시점이든 베팅액보다 적습니다.

   컨트랙트가 강제하지 못하는 것이 하나 있습니다. 서버가 정산 기한까지 정산을 보내지 않으면 컨트랙트는 진 판이든 이긴 판이든 베팅액 전액을 돌려줍니다. 그래서 "서버가 제때 정산한다"는 서버가 지켜야 하는 조건입니다. **독립 검토(§12)는 플레이어가 서버를 멈추게 만들 수 있고, 그렇게 해서 불리한 판을 전액 회수할 수 있다는 것을 찾았습니다. 검토자의 모의 계산으로는 이 방법의 환수율이 약 105%입니다.** 이 문서의 이전 판은 "다른 수단으로 돈을 빼내는 길은 찾지 못했다"고 적었는데, 그 문장은 틀렸습니다. 이 문제는 수정 진행 중 — 최종 확인 후 갱신.

   감사 문서(`docs/exploit-audit.md`)의 항목은 36개이고 21개는 고쳐서 막았고 8개는 구조상 불가능했으며 7개는 받아들인 위험입니다(§4. X33~X36은 독립 검토 뒤에 추가된 항목이고, 이 개수는 최종 확인 후 갱신합니다). 개발 중의 감사에서 실제로 뚫려 있던 것은 하나였고(한 주소가 게임을 여러 개 열어 하우스 잔액을 묶는 것. 돈을 빼내지는 못함) 고쳤습니다. 개발 중에 거친 검토들은 저장소에 기록으로 남아 있지 않습니다. 결과가 저장소에 남아 있는 검토는 §12의 독립 검토 한 번입니다.
2. **시험한 전략에 대해 통계적으로 한정된 것.** 전략 묶음을 크기별로 24 / 28 / 32개 만들어 각각 3,000,000 / 5,000,000 / 11,000,000판씩 돌렸습니다. 이 묶음의 대부분은 "최대한 잘하는 전략"이 아닙니다. 9×9의 32개를 보면 정해진 걸음 수에서 그만두는 규칙이 17개, 조건이 맞으면 포기하는 규칙이 5개, 가정한 플레이어 집단을 흉내 낸 것이 4개, 이 표에서는 베팅 직후 포기와 똑같이 행동하게 된 것이 3개(환수율 정확히 95.000%), 그만두지 않고 걷기만 하는 것이 1개(환수율 약 90.1%)입니다. **출구를 노리면서 상한 근처까지 가는 전략은 크기마다 `value-table`과 `value-lsm` 둘이고, 둘은 같은 학습 방식에서 나온 한 계열입니다.** 그 가운데 더 잘하는 `value-lsm`도 평균적으로 베팅액의 4.19% / 4.61% / 4.65%를 잃습니다. 묶음에는 "베팅 직후 포기", "한 걸음 보고 포기", "첫 갈림길에서 포기", "시작 방향이 마음에 들 때만 계속" 같은 날먹 시도도 들어 있고 모두 95% 이하입니다.

   묶음 밖에서 따로 시험한 적대 전략은 둘인데, 그중 `rollout(32)`는 이 실행에서 5×5와 9×9의 모든 판을, 7×7의 절반을 베팅 직후 포기했습니다(§6.8). 실제로 판을 둔 적대 전략은 `value-lookahead-all` 하나이고 `value-lsm`과 같은 가치표를 씁니다. 97.5% 상측 신뢰한계의 최댓값 96.13%는 손익분기 100%와 스펙 상한 96.5%보다 아래이지만, 그 값은 판을 두지 않은 `rollout(32)`의 짝 추정치에 붙은 것입니다. 판을 둔 전략 가운데 가장 높은 상측 한계는 95.99%입니다. 따라서 "시험한 어떤 전략도 96.13%를 넘지 못했다"는 말이 실제로 기대는 것은 가치표 전략 한 계열과, 20칸 이하 격자에서의 정확성 게이트(아래 3)입니다.
3. **가정으로 남는 것.** 시험하지 않은 전략 가운데 더 좋은 것이 없다는 것은 증명하지 못했습니다. 미로를 전부 나열할 수 있는 작은 격자(3×3, 4×4, 5×4)에서는 수학적으로 최적인 플레이를 정확히 계산할 수 있는데, 거기서 최고 전략과 최적의 차이는 최대 0.144%p였습니다. 플레이어가 이익을 내려면 그 차이가 약 4%p여야 합니다. 다만 이 차이는 격자가 커질수록 커지는 방향이고(0.00 → 0.04 → 0.14%p), 실제 게임 크기에서는 계산할 수 없습니다. 이 부분은 받아들인 위험으로 적어 두었습니다(§4의 X26).

요약하면 **컨트랙트를 속여 돈을 빼내는 길은 막혀 있고, 서버를 멈추게 해 전액 회수를 받아 내는 길은 독립 검토에서 발견되어 고치는 중이며(최종 확인 후 갱신), 실력으로 돈을 버는 길은 시험한 범위에서 없고(그 범위는 가치표 전략 한 계열), 시험하지 않은 전략까지 없다는 것은 가정**입니다.

### 튜닝이 내놓은 답과 두 표 사이의 선택

"흥미를 잃지 않게"와 "하우스가 더 잘 먹게"를 숫자로 맞추려고, 평범한 플레이어(출구 방향으로만 가는 사람)는 베팅액의 85% 이상을 돌려받아야 한다는 기준을 **가정**으로 세웠습니다. 결과는 이렇습니다.

- 그 기준을 지키면서 하우스 수익을 더 올리는 표는 찾지 못했습니다. 지금 적용된 "기본 표"는 기준을 지키도록 손본 것이고, 손보기 전과 비교한 하우스 수익 변화는 −0.003%p입니다(95% 하측 한계 −0.025%p). 즉 더 벌지 않습니다. 이 비교의 기준은 이미 큰 크기를 9×9로 줄인 표(25.764%)입니다. 처음의 10×10 후보들과 비교하면(ii 26.080%, iii 26.335%. 큰 크기는 축소 표본) 지금 적용된 표의 25.761%는 약 0.3~0.6%p 낮습니다. 85% 기준을 지키는 데 든 값입니다.
- 기준을 지키려고 큰 크기를 10×10에서 9×9로 줄였습니다. 그래서 큰 크기의 배율이 18.47배로, 가정했던 "20배 이상"에 못 미칩니다.
- 하우스 수익을 실제로 올리는 방법은 85% 기준을 내려놓는 것입니다. 그렇게 고른 "하우스 최대 표"도 인증해 두었습니다.

| | 기본 표 (지금 적용됨) | 하우스 최대 표 (인증 완료, 미적용) |
|---|---|---|
| 크기와 배율 | 5×5 2.6088배, 7×7 6.6112배, 9×9 18.4695배 | 5×5 2.3408배, 7×7 5.8113배, 10×10 26.5572배 |
| 첫 걸음 뒤 환불 가능액 | 73% | 90% (요청하신 "걸음마다 조금씩 감소"에 더 가까움) |
| 하우스 수익 (가정한 플레이어 구성에서) | 25.761% ± 0.047%p | 31.627% ± 0.043%p |
| 평범한 플레이어가 돌려받는 비율 | 87.28% / 86.27% / 85.40% | 78.31% / 75.83% / 71.41% |
| 실수가 잦은 플레이어가 돌려받는 비율 | 77.02% / 71.33% / 66.30% | 69.11% / 62.70% / 53.75% |
| 잔고 50배로 1배씩 걸 때 버티는 판 수 (중앙값) | 347 / 268 / 160판 | 218 / 172 / 103판 |
| 최고 전략이 한 걸음 안에 포기하는 판의 비율 | 0.00% / 38.56% / 0.00% | 39.09% / 38.56% / 38.43% |
| 최고 전략 상대 하우스 몫 | 4.19% / 4.61% / 4.65% | 4.10% / 4.20% / 4.25% |

하우스 최대 표는 수익이 5.867%p 높지만 평범한 플레이어의 손실이 1.7~2배로 커지고, 잘하는 플레이어는 열 판 중 네 판을 한 걸음 만에 접습니다. 어느 쪽이 "흥미를 잃지 않는" 쪽인지는 실제 플레이어 데이터 없이는 판단할 수 없어서, 가정을 지킨 기본 표를 적용해 두고 선택을 남겼습니다. 바꾸는 방법은 §6.9에 있습니다.

### 숫자를 믿기 전에 읽어야 할 것

1. **하우스 수익 25.761%와 31.627%는 가정 위의 숫자입니다.** 플레이어의 35%는 출구 방향으로만 가고, 25%는 가끔 실수하고, 15%는 최고 수준이라는 식의 구성은 실제 데이터가 아니라 계획 단계에서 정한 값입니다(§6.2).
2. **튜닝 결과가 "개선됨"으로 기록되지만 하우스가 더 번다는 뜻이 아닙니다.** 85% 기준을 어긴 표를 지키는 표로 바꿨다는 뜻입니다(§6.5).
3. **85% 기준은 아슬아슬하게 맞췄습니다.** 9×9에서 채택한 값은 85.403%(95% 신뢰구간 85.17~85.63%)이고, 같은 방식으로 시험한 다른 두 값은 84.979%와 84.799%로 떨어졌습니다. 이 정도 차이는 우연에 가깝습니다.
4. **7×7은 잘하는 플레이어에게 "할 이유"가 얇습니다.** 최고 전략이 38.56%의 판에서 한 걸음 안에 포기하고, 끝까지 하는 것이 베팅 직후 포기하는 것보다 평균 0.39%p 나을 뿐입니다.
5. **"강한 전략"은 보기보다 적습니다.** 인증 묶음 가운데 세 개는 이 표에서 "베팅 직후 포기"와 똑같이 행동해 추가 정보를 주지 않습니다. 적대 전략 `rollout(32)`도 5×5와 9×9에서는 모든 판을, 7×7에서는 절반을 베팅 직후 포기했습니다. 출구를 노리며 상한 근처까지 간 전략은 `value-lsm`, `value-table`, `value-lookahead-all` 셋이고 모두 같은 가치표 계열입니다(§6.8).
6. **하우스 몫이 스펙의 4% ± 0.5%p를 벗어난 크기가 있습니다.** 7×7 4.61%, 9×9 4.65%. 하우스에 유리한 쪽입니다(§6.6).

### 최종 판정

**수정 진행 중 — 최종 확인 후 갱신.** 이 문서의 이전 판은 전체 검증 `pnpm verify:all`이 종료 코드 0으로 끝난 것을 근거로 "완료"라고 적었습니다. 그 뒤 독립 검토가 서버 중단 뒤 전액 회수를 포함한 문제를 찾았고(§12) 지금 고치는 중입니다. 수정이 끝나면 `pnpm verify:all`을 다시 돌려 이 판정을 갱신합니다. 권고 항목 하나(탐색 에이전트 시나리오)는 실행하지 않았습니다(§8).

판정을 읽는 법도 바로잡습니다. `pnpm verify:all`의 "인수 기준 PASS"는 기준 하나하나를 따로 실행해 확인했다는 뜻이 아니라 **묶음 단위 판정**입니다. 어떤 기준이 PASS라는 것은 그 기준에 배정된 검사 묶음이 모두 종료 코드 0으로 끝났고, 그 묶음이 테스트 묶음이면 그 안에 그 기준의 이름을 제목에 단 테스트가 있다는 뜻입니다. 어떤 테스트가 어떤 기준을 증명했는지를 실행 기록으로 추적하지는 않습니다. 기준 79개 가운데 28개(권고 항목 포함)는 배정된 묶음에 이름 붙은 테스트가 아예 없고, 명령(인증 확인, 정확 계산 확인, 표 확인, 브라우저 시나리오 실행, 감사·보고서 문서 검사, ABI 검사, 소유 경로 검사, 빌드)이 종료 코드 0으로 끝났다는 것만으로 PASS입니다(§7).

## 2. 직접 돌려 보는 방법

필요한 것: Node 25 이상, pnpm, Foundry(`anvil`, `forge`, `cast`).

```sh
pnpm install
pnpm dev:up      # 로컬 체인(8545) 시작 → 컨트랙트 배포와 하우스 예치 → 앱 빌드 → http://localhost:3000
pnpm dev:down    # 위에서 띄운 두 프로세스만 종료
```

`pnpm dev:up`이 끝나면 터미널에 앱 주소, 체인 주소, 컨트랙트 주소가 나옵니다. 브라우저에서 `http://localhost:3000`을 열면 다음 순서로 보입니다.

1. "개발용 지갑으로 연결"을 누릅니다. 로컬 체인의 테스트 계정이 연결되고 잔액이 표시됩니다.
2. "미로 크기"에서 S(5×5칸, 2.6088배), M(7×7칸, 6.6112배), L(9×9칸, 18.4695배) 가운데 하나를 고릅니다. 크기마다 "출구 도착 시 … ETH"가 적혀 있습니다(입력한 베팅 금액으로 출구에 닿으면 받는 금액. 금액을 넣기 전에는 "출구 도착 시 —").
3. 베팅 금액(최소 0.001, 최대 0.1 ETH)을 넣으면 걸음별 환불 일정이 표로 나옵니다. 베팅 직후 95%, 첫 걸음 뒤 73%라는 안내도 함께 나옵니다.
4. "베팅하고 시작"을 누르면 보드가 나옵니다. 지나온 칸과 현재 칸의 벽만 보이고 나머지는 가려져 있습니다. 화면의 버튼이나 방향키, WASD로 움직입니다.
5. "지금 그만두면 받는 금액"과 "출구에 도착하면" 받는 금액이 항상 보이고, "… ETH 받고 그만하기" 버튼으로 캐시아웃합니다. 120초 동안 움직이지 않으면 자동으로 캐시아웃되고, 베팅 후 900초가 지나면 강제 정산됩니다. 남은 시간이 화면에 나옵니다.
6. 판이 끝나면 결과와 받은 금액, 정산 트랜잭션이 나오고, "이 판이 공정했는지 검증하기"를 누르면 공개된 시드로 미로를 다시 만들어 플레이 중 본 벽과 한 칸씩 대조합니다.

## 5. 날먹 감사에서 한 일

- 미리 정한 공격 30가지를 하나씩 시도하고, 그 밖의 공격을 코드 읽기 6가지와 실행 중인 시스템 공격 6가지로 더 찾았습니다. 항목마다 가설, 시도, 결과, 조치, 이를 고정하는 테스트 이름이 `docs/exploit-audit.md`에 있습니다.
- 찾아서 고친 것: 한 주소가 티켓을 미리 여러 장 받아 두면 "주소당 한 판" 규칙을 우회해 게임을 여러 개 열 수 있었습니다. 돈을 빼내지는 못하지만 하우스 잔액을 묶을 수 있어 고쳤습니다.
- 정보가 새는지: 서버 응답에는 현재 칸(재개 시에는 지나온 칸)의 벽만 들어 있고, 관측이 같은 서로 다른 두 미로에 대해 응답이 바이트 단위로 같다는 것을 테스트로 고정했습니다. 진행 중인 게임의 시드는 `/reveal`로 얻을 수 없습니다.
- 지연으로 전액 회수를 유도할 수 있는지: 방치, 시작하지 않기, 기한 직전 시작, 수령을 일부러 실패시키는 컨트랙트 지갑 네 경우 모두 회수가 성공하지 않습니다. 이 네 경우에 "서버를 멈추게 만들기"는 들어 있지 않았습니다.
- 독립 검토가 더 찾은 것: 플레이어가 서버를 멈추게 한 뒤 전액 회수를 받는 길(X33)과 주소 잠김(X34)입니다. 수정 진행 중 — 최종 확인 후 갱신(§12).

## 6. 시뮬레이션과 튜닝

### 6.1 시뮬레이션 규모

요청은 "1,000회 이상"이었습니다. 1,000판으로는 환수율 오차가 ±7~24%p라 아무것도 가릴 수 없어서, 전략 하나 × 크기 하나(아래 "셀")마다 수백만 판을 돌렸습니다. 판 수는 실행 전에 고정했고 도중에 줄이지 않았습니다.

| 크기 | 셀당 판 수 | 요청한 1,000판 대비 | 셀 수 | 이 크기의 인증 판 수 | 최고 전략의 95% 오차 폭 | 1,000판이었다면 |
|---|---|---|---|---|---|---|
| 5×5 | 3,000,000 | 3,000배 | 24 | 72,000,000 | ±0.129%p | ±7.1%p |
| 7×7 | 5,000,000 | 5,000배 | 28 | 140,000,000 | ±0.162%p | ±11.5%p |
| 9×9 | 11,000,000 | 11,000배 | 32 | 352,000,000 | ±0.227%p | ±23.8%p |

튜닝 전체에서 시뮬레이션한 판은 최소 7,257,622,682판이고(배율을 맞추는 보정 11.1억, 인증 29.8억, 전략 학습과 탐색 약 25억, 작은 격자 정확 계산 6.3억 등), 걸린 시간은 6.80시간입니다(`docs/tuning-report.md`에는 6.81시간으로 찍혀 있습니다. 표 전환 명령을 고치느라 보고서를 다시 만들 때 캐시를 읽은 1.6초가 누적 시간에 더해져 반올림이 넘어간 것이고, 새로 시뮬레이션한 판은 없습니다). 배율을 맞출 때 쓴 난수와 인증할 때 쓴 난수는 서로 겹치지 않게 나눴습니다.

### 6.2 가정 목록

실제 플레이어 데이터가 없어서 아래는 전부 **가정**입니다. 하우스 수익 수치, 흥미 기준의 판정, 표의 선택이 여기에 의존합니다.

| 가정 | 값 |
|---|---|
| 플레이어 집단 구성 | 출구 방향으로만 가는 사람(`naive-greedy`) 35%, 10% 확률로 실수하는 사람(`sloppy-greedy`) 25%, 걸음마다 일정 확률로 그만두는 사람(`nervous`) 20%, 아무 방향이나 가는 사람(`random-walk`) 5%, 최고 수준 15% |
| 크기 이용 비중 | 작은 크기 50%, 중간 35%, 큰 크기 15% |
| 흥미 범위 | 평범한 플레이어 환수율 85% 이상, 실수 잦은 플레이어 환수율 50% 이상, 표시 배율 2 / 5 / 20배 이상, 첫 걸음 뒤 환불 60% 이상·최단 경로 뒤 환불 20% 이상, 평범한 플레이어의 승리 빈도 25~45% / 8~20% / 2~6%, 세션 중앙값 200 / 150 / 50판 이상 |

기본 표가 이 가정 가운데 지키지 못한 것은 큰 크기의 표시 배율입니다(18.47배, 기준 20배). 나머지는 지켰습니다.

### 6.3 정확성 게이트: 최고 전략이 정말 최고에 가까운가

배율은 "시험한 전략 가운데 가장 잘하는 것"에 맞춥니다. 그 전략이 수학적 최적과 얼마나 떨어져 있는지를, 미로를 전부 나열할 수 있는 작은 격자에서 쟀습니다. 최고 전략의 환수율이 정확히 96.00%가 되는 배율에서 최적이 얼마나 더 받는지가 간격이고, 세 격자 모두 0.50%p 이하면 통과입니다.

| 곡선 | 3×3 (미로 112개) | 4×4 (60,032개) | 5×4 (2,483,688개) | 택한 분기 |
|---|---|---|---|---|
| 기본 표의 5×5·7×7 곡선 | −0.000%p | 0.044%p | 0.144%p | 통과. 실패 분기 없음 |
| 기본 표의 9×9 곡선 | −0.007%p | −0.005%p | 0.008%p | 통과. 실패 분기 없음 |
| 하우스 최대 표의 곡선 | −0.003%p | −0.002%p | 0.011%p | 통과. 실패 분기 없음 |

### 6.8 적대 전략: 96.5%와 나란히

인증 묶음 밖의 전략 두 개를 따로 시험했습니다. `rollout(32)`는 가능한 미로를 32개씩 뽑아 끝까지 플레이해 보고 정하도록 만든 전략이고, `value-lookahead-all`은 모든 결정에서 한 걸음 앞을 정확히 계산하는 전략입니다. 둘 다 느려서, 최고 봇과 같은 미로에서 짝으로 돌려 차이를 쟀습니다. 스펙 상한 96.5%와 나란히 보면 다음과 같습니다. 표의 점추정은 그 전략이 실제로 돌려받은 비율이 아니라 "최고 봇의 환수율 + 같은 미로에서 잰 평균 차이"로 만든 짝 추정치입니다.

| 크기 | rollout(32) 점추정 (96.5%와의 차) | 상측 한계 | 짝 수 | value-lookahead-all 점추정 (96.5%와의 차) | 상측 한계 | 짝 수 |
|---|---|---|---|---|---|---|
| 5×5 | 94.545% (−1.955%p) | 95.063% | 199,773 | 95.825% (−0.675%p) | 95.986% | 100,000 |
| 7×7 | 87.499% (−9.001%p) | 88.025% | 579,473 | 95.270% (−1.230%p) | 95.518% | 100,000 |
| 9×9 | 95.340% (−1.160%p) | 96.126% | 1,000,000 | 95.468% (−1.032%p) | 95.752% | 400,000 |

9×9의 `rollout(32)`는 짝 수 상한 1,000,000쌍에 걸려 오차 폭이 ±0.752%p로 목표(±0.5%p)보다 넓습니다. 판정은 상측 한계로 했고 99.0% 아래입니다.

**`rollout(32)`는 이 실행에서 강한 전략이 아니었습니다.** 저장된 결과를 다시 합산해 보면 `rollout(32)`는 5×5의 199,773판과 9×9의 1,000,000판을 전부 베팅 직후 포기했습니다(승리 0판, 실제 환수율 정확히 95.000%). 7×7에서는 579,473판 중 289,878판(50.02%)을 베팅 직후 포기했는데, 시작 칸이 동쪽으로 뚫린 판 전부입니다(실제 환수율 87.589%). 원인은 구현에 있습니다(`packages/sim/src/bots/rollout.ts`). 표본을 뽑는 난수의 시드를 "지금까지 본 것"으로 정하는데, 걷기 전에 볼 수 있는 것은 시작 방향 둘뿐이라 첫 결정이 판마다 새 표본이 아니라 방향마다 고정된 표본 32개 한 벌로 내려집니다. 그래서 위 표의 `rollout(32)` 열, 특히 전체에서 가장 높은 상측 한계 96.126%는 매 판 95%만 돌려받은 봇에 붙은 숫자이고, 그 폭은 짝이 된 최고 봇의 분산에서 나온 것입니다. 적대 전략 검사에서 실제로 판을 두며 검사한 전략은 `value-lookahead-all` 하나이고, 이 전략은 `value-lsm`과 같은 가치표를 씁니다. 시드에 판마다 다른 값을 섞으면 고쳐지지만, 그 파일이 시뮬레이터 코드 해시에 들어 있어 인증(약 7시간)을 전부 다시 해야 합니다. 이번에는 고치지 않고 알려진 한계로 남기며 다음 재튜닝 때 고칩니다(§11).

인증 묶음에 대해 알아 둘 점: 묶음의 `region-heuristic`, `param-search`, `harmonic-lsm`은 이 표에서 첫 걸음 전에 캐시아웃하는 쪽으로 수렴해 환수율이 정확히 95.000%입니다. 판정에는 포함되지만 "베팅 직후 포기"와 같은 정보만 줍니다. 9×9의 묶음 32개는 정해진 걸음 수에서 그만두는 규칙 17개, 포기 규칙 5개, 가정한 플레이어 집단 4개, 방금 말한 3개, 그만두지 않고 걷는 `harmonic`(90.14%), 그리고 `value-table`(95.28%)과 `value-lsm`(95.35%)입니다. 출구를 노리며 상한 근처까지 가는 전략은 `value-table`, `value-lsm`, `value-lookahead-all` 셋이고 모두 같은 가치표 계열입니다. "시험한 어떤 전략도 96.13%를 넘지 못했다"는 결론은 이 한 계열과 20칸 이하 격자의 정확성 게이트(§6.3)에 기대고 있습니다.

```sh
pnpm tuning:apply packages/sim/reports/tuning.house-max.json && pnpm dev:down && pnpm dev:up && pnpm tuning:check

pnpm tuning:apply packages/sim/reports/tuning.candidate.json && pnpm dev:down && pnpm dev:up && pnpm tuning:check
```

계획과 이 문서의 이전 판은 확인(`pnpm tuning:check`)을 재배포보다 앞에 둔 순서를 적었는데, 그 순서는 확인에서 멈춥니다. `pnpm tuning:check`는 배포된 컨트랙트가 새 표와 일치하는지도 검사하는데 그 시점에는 아직 옛 표의 컨트랙트가 떠 있기 때문입니다. 그러면 표 파일만 바뀌고 서버는 옛 표로 도는 상태가 남습니다. 튜닝 보고서, 스펙 이탈 문서, 문서 검사(`pnpm report:check`)를 모두 위 순서로 고쳤고, 문서 검사는 이제 멈추는 순서가 문서에 적혀 있으면 실패합니다.

이 순서로 하우스 최대 표로 바꿨다가 기본 표로 돌아오는 것을 한 번씩 실행해 확인했습니다(독립 검토 전의 코드에서). 하우스 최대 표를 적용한 상태에서 공용 모듈, 서버·화면, 컨트랙트 테스트도 통과했습니다. 그 상태에서 브라우저 시나리오는 돌리지 않았습니다. 이번에 추가한 고정 벡터 테스트(§12)는 두 인증 표의 값을 모두 담고 있어 표를 바꿔도 따라옵니다. 저장소 밖 복사본에 하우스 최대 표를 넣어 컨트랙트 테스트와 공용 모듈의 해당 테스트가 통과하는 것을 확인했습니다. 인증되지 않은 새 표를 적용하면 이 테스트는 "이 표의 벡터가 없다"며 실패하고, `packages/shared/test/vectors/make-contract-vectors.ts`로 벡터를 추가해야 합니다.

인수 기준은 계획이 정한 합격 조건 79개입니다(그중 하나는 권고 항목이라 집계에서 빠집니다). `pnpm verify:all`의 결과는 `.data/verify-all/result.json`에, 단계별 로그는 `.data/verify-all/logs/`에 남습니다.

**인수 기준 판정이 뜻하는 것.** `pnpm verify:all`은 기준마다 따로 검사를 돌리지 않습니다. 검사 묶음 15개를 돌리고, 계획이 기준마다 배정한 묶음의 결과로 그 기준을 판정합니다. 독립 검토의 지적에 따라 이 판정을 다음과 같이 바꿨고, 출력과 결과 파일에도 같은 설명이 들어갑니다.

- 기준이 PASS이려면 배정된 묶음이 모두 종료 코드 0이어야 하고, 그 가운데 **테스트 묶음마다** 그 기준의 이름을 제목에 단 테스트가 있어야 합니다. 전에는 배정된 묶음들의 폴더를 한데 합쳐 글자를 찾았고 주석도 셌습니다. 그래서 통합 테스트 묶음에 이름 붙은 테스트가 없는 AC-S2와, 주석에만 이름이 있던 AC-M6이 PASS로 나왔습니다. 두 기준의 내용은 통합 테스트가 실제로 확인하고 있어서(공개 조건은 AC-S10 테스트, 미로 재현은 출구 판 테스트) 해당 테스트의 제목에 이름을 붙이면 됩니다. 그 제목 수정은 서버 테스트 수정과 함께 반영합니다(수정 진행 중 — 최종 확인 후 갱신). 그 전까지 `verify:all`은 이 둘을 FAIL로 표시합니다.
- 기준 79개 가운데 28개는 배정된 묶음에 테스트 묶음이 없어서, 명령이 종료 코드 0으로 끝났다는 것만으로 PASS입니다.
- 권고 기준 AC-A7은 브라우저 시나리오 묶음 전체의 결과가 아니라 시나리오 09가 기록한 결과를 그대로 따릅니다. 09를 실행하지 않았으면 NOT-RUN으로 표시되고, 집계에도 종료 코드에도 들어가지 않습니다.
- 소유 경로 검사(AC-I2)는 HEAD와 달라진 파일만 비교하므로 달라진 파일이 없으면 비교한 것이 없습니다. 이제 몇 개를 비교했는지를 결과에 적고, 0개면 그렇게 적습니다.
- 결과 파일은 그 결과가 나온 커밋과 작업 트리의 상태(깨끗한지, 달라진 내용의 지문)를 기록합니다. `pnpm report:check`는 지금 트리와 다른 트리에서 나온 결과 파일을 거부합니다. 코드나 문서를 고친 뒤에는 `pnpm verify:all`을 다시 돌려야 합니다.

자동 검사 밖에서 한 번 수동으로 확인한 것: `pnpm dev:up`으로 띄운 서버(기본 표, 테스트 장치 꺼짐)를 상대로, 미로를 모르는 채 무작위 시드로 네 판을 돌렸습니다(5×5 패배, 7×7 두 걸음 뒤 캐시아웃, 9×9 패배, 9×9 한 걸음 뒤 캐시아웃). 네 판 모두 체인에서 정산됐고, 시드는 끝난 뒤에만 공개됐으며, 공개된 시드로 다시 만든 미로가 플레이 중 본 벽과 일치했습니다. 화면을 거치지 않았고 출구에 도착한 판은 없었으며, 저장소의 검사 묶음에 들어 있지 않습니다.

### 이번 마무리 단계에서 고친 것

- 정산 트랜잭션 표시: 서버가 보낸 정산 트랜잭션이 유실되어 다시 보내진 경우, 화면이 처음 보낸(채굴되지 않은) 트랜잭션 번호를 계속 보여 주던 문제를 고쳤습니다. 이제 화면은 체인이 "이 트랜잭션이 이 게임을 정산했다"고 확인해 준 번호만 보여 주고, 그때까지 서버에 계속 묻습니다.
- 배율 표시: 인증된 배율은 소수 넷째 자리까지 있는데 화면이 둘째 자리로 반올림해 2.6088배를 "2.61배"로 보여 주고 있었습니다. 실제보다 크게 보이지 않도록 정확히 표시하게 고쳤습니다. 받는 금액 표시는 원래 정확했습니다.
- 9×9 크기: 고정 검증 벡터와 미로·환불·검증 테스트, 시뮬레이터 테스트에 9×9를 추가했습니다. 브라우저 시나리오는 표에 있는 모든 크기의 환불 일정을 확인하고 세 크기를 각각 플레이하도록 바꿨습니다.

### 확인하지 못했거나 가정인 것

- 실제 무작위 시드로 도는 자동 종단 실행은 없습니다. 브라우저 시나리오는 기본 표로 돌릴 때도 테스트용 시드 생성 장치를 켭니다.
- 흥미 범위, 플레이어 집단 구성, 크기 이용 비중은 가정입니다(§6.2).
- 5×5 이상에서 최고 전략과 수학적 최적의 간격은 가정입니다(§6.3).
- 선택되지 않은 후보의 큰 크기 수치는 축소 표본이며 배포할 수 없습니다(§6.4).
- 로컬 Anvil 체인에서만 실행했습니다.
- 탐색 에이전트 시나리오(권고 항목)는 실행하지 않았습니다(§8).
- 하우스 최대 표를 적용한 상태의 브라우저 시나리오는 돌리지 않았습니다.
- 브라우저 확장 지갑으로 베팅부터 정산까지 가 본 적이 없습니다. 그 경로는 가짜 공급자를 쓴 단위 테스트만 있고, 브라우저 시나리오와 수동 확인은 전부 개발용 지갑으로 했습니다(§3의 16).
- 독립 검토의 결과와 수정 상태는 §12에 있습니다. 그 가운데 네 항목은 아직 고치는 중입니다.

### 알려진 한계

- **적대 전략 `rollout(32)`는 이번 인증에서 사실상 판을 두지 않았습니다(§6.8).** 적대 전략 검사에서 실제로 검사된 것은 `value-lookahead-all` 하나입니다. 다음 재튜닝 때 고치고 다시 인증해야 합니다.
- **시뮬레이터 코드 해시가 저장된 결과를 좌우하는 코드를 전부 덮지는 않습니다.** 해시는 저장된 결과가 지금 코드에서 나온 것인지 가리는 데 쓰는데, 다음은 해시 밖에 있습니다. 학습에 쓸 난수열을 고르는 곳(`packages/sim/src/runner.ts:427-443`)은 저장 키에 들어가는 값과 따로 적힌 글자로 난수열을 고릅니다. 작은 격자의 미로를 전부 나열하는 코드(`packages/sim/src/exact.ts:36`)와 공용 타입 정의(`packages/shared/src/types.ts`)도 해시 밖입니다. 테스트(`packages/sim/test/cache.test.ts:110`)는 이 제외를 그대로 고정해 두고 있습니다. 지금 저장된 결과는 이 파일들이 바뀌기 전에 만들어져 문제가 없습니다. 해시 범위를 넓히면 해시 값이 바뀌어 인증(약 7시간)을 전부 다시 해야 하므로 다음 재인증 때로 미뤘습니다. 그때까지 이 파일들을 고치면 저장된 결과가 낡았는데도 검사가 알아채지 못할 수 있습니다.
- **실제 체인에서의 수지는 따져 보지 않았습니다.** 정산 트랜잭션의 가스비는 하우스가 냅니다. 최소 베팅 0.001 ETH에서 하우스 몫 5%는 0.00005 ETH(5×10¹³ wei)라, 가스비가 그보다 비싼 체인에서는 최소 베팅 판마다 하우스가 손해를 봅니다. 서버는 보낸 정산 트랜잭션이 막혔을 때 같은 순번으로 수수료를 올려 다시 보내는 처리를 하지 않습니다. 로컬 체인에서는 드러나지 않는 문제입니다.

## 8. aside 브라우저 시나리오 결과와 사용한 경로

aside는 명령줄에서 브라우저를 조작하는 도구입니다. 별도의 테스트 브라우저가 아니라 **사용자의 실제 브라우저를 조작합니다.** 시나리오는 자기가 연 탭만 다루고 끝나면 닫으며, `127.0.0.1`의 저장소 가운데 `maze:`로 시작하는 항목만 건드립니다.

- 입력 경로: `aside repl`(명령줄에서 페이지의 버튼을 누르고 값을 입력). 읽기 경로: 같은 `aside repl`로 페이지의 DOM을 직접 읽음. 두 경로가 실제로 되는지는 시나리오 전에 능력 탐지 단계가 확인합니다.
- 판정: 체인 확인, HTTP 확인, 화면(DOM) 확인이 모두 실행되어 통과해야 PASS입니다. 화면 확인을 실행하지 못하면 PASS가 아니라 BLOCKED로 셉니다.

시나리오 실행기에서 바뀐 것: 테스트용 시드 생성 장치의 비밀값이 저장소에 고정된 글자로 적혀 있었는데, 이제 실행할 때마다 무작위로 새로 만들어 서버와 경로 계산 도구에 같은 값을 넘깁니다(재현하려면 로그에 찍힌 값을 `MAZE_TEST_SEED_SECRET`으로 넘김). 테스트 장치를 켠 채 스택을 띄우는 명령은 한 군데(`e2e/aside/lib.sh`의 `dev_up`)에서만 만들고, `scripts/dev-up.sh`의 명시적 스위치 `--allow-test-hooks`를 붙입니다. 서버가 죽은 상태가 유지되어야 하는 시나리오(05, 10, 11)는 앱을 다시 띄우는 감시 프로세스를 먼저 멈춥니다. 이 변경들은 문법 검사만 했고 브라우저 시나리오로는 아직 돌려 보지 않았습니다(최종 확인 후 갱신). 게임 도중에 앱을 죽이고 감시 프로세스가 다시 띄우는 것을 확인하는 시나리오는 아직 없습니다.

## 9. BLOCKED 항목

없습니다. 세 번 시도해도 통과하지 못해 중단한 게이트가 없고, `pnpm verify:all`에서 BLOCKED로 표시된 인수 기준도 없습니다(독립 검토 전의 실행 기준. 수정 뒤 다시 돌려 확인합니다 — 최종 확인 후 갱신).

참고로, 경제 쪽에서 막히는 경우인 BLOCKED(경제)(어떤 배율로도 상한을 못 맞추거나, 후보를 모두 소진하거나, 시뮬레이션 시간 한도 30시간을 넘는 경우)가 났다면 운영용 표가 존재하지 않고 게임은 테스트 표 모드로만 기동됐을 것입니다. 이번 실행에서는 일어나지 않았습니다. 시뮬레이션은 6.80시간에 끝났습니다.

## 10. 알아 두어야 할 동작과 고른 상수

- **지급이 미뤄질 수 있습니다.** 컨트랙트는 지급할 때 가스를 30,000까지만 넘깁니다. 받는 주소가 컨트랙트 지갑이나 위임 지갑이라 그 안에 받지 못하면, 돈은 컨트랙트의 `pendingWithdrawals`에 적립되고 플레이어가 따로 인출해야 합니다. 일반 지갑은 해당하지 않습니다.
- **`/reveal`은 끝난 게임 말고도 시드를 공개합니다.** 베팅에 쓰이지 않고 만료된 티켓과, 기한 초과로 회수된 게임의 서버 시드도 공개합니다. 진행 중인 게임은 공개하지 않습니다.
- **테스트 전용 코드가 저장소에 남아 있습니다.** 시드를 게임 번호에서 유도하는 장치, 테스트 표, 화면 내용을 서버로 보내는 `TestBeacon`, `/api/test/ui-snapshot` 경로입니다. 이를 막는 것은 환경 플래그 `MAZE_ALLOW_TEST_HOOKS` 하나입니다(로컬 체인 번호는 항상 같아서 구분 기준이 못 됩니다). 플래그가 꺼져 있으면 테스트 경로는 404이고, `pnpm start:web`은 플래그가 켜져 있으면 기동을 거부하며, 어떤 `.env` 파일에도 플래그를 쓰지 않습니다. 독립 검토 뒤의 수정으로 `pnpm dev:up`도 테스트용 플래그가 환경에 하나라도 있으면 명시적 스위치(`--allow-test-hooks`) 없이는 아무것도 띄우지 않게 바뀌는 중입니다(수정 진행 중 — 최종 확인 후 갱신).
- **정산은 서버가 서명한 결과를 가진 누구나 제출할 수 있습니다.** 평소에는 서버의 중계 계정이 보냅니다. 서명이 게임 번호와 플레이어를 묶고 있어서 남이 제출해도 결과와 받는 사람은 바뀌지 않습니다(§3의 15).
- **독립 검토 뒤 서버 쪽에서 바뀌는 동작(수정 진행 중 — 최종 확인 후 갱신).** `pnpm dev:up`은 앱이 죽으면 다시 띄우는 감시 프로세스 아래에서 앱을 돌립니다. `GET /api/health`는 서버가 실제로 일하고 있을 때만 200을 줍니다. 서버를 직접 띄울 때(`pnpm start:web`)는 데이터 폴더 `MAZE_DATA_DIR`을 절대 경로로 반드시 지정해야 합니다. 티켓 요청(`POST /api/games`)에는 지갑 서명이 필요합니다. 정확한 내용은 서버 쪽 수정의 최종 보고로 확정합니다.
- **`/start`를 부르지 않은 게임도 시계가 돕니다.** 베팅만 하고 시작하지 않으면 120초 뒤 자동 캐시아웃되어 5%를 잃습니다.
- **재튜닝은 컨트랙트 재배포입니다.** 배율과 환불 표가 컨트랙트에 들어 있어서, 표를 바꾸면 새 컨트랙트를 배포해야 합니다.
- **고른 상수.** 최소 베팅 0.001 ETH, 최대 베팅 0.1 ETH, 방치 자동 캐시아웃 120초, 강제 정산 900초, 정산 기한 1800초(모두 체인 시각 기준, 베팅이 블록에 들어간 때부터), 티켓 유효 시간 120초, 지급 가스 한도 30,000, 하우스 초기 예치 100 ETH.
